## Overview

The inventory system is the core of the entire POS. It is the single source of truth for all product data and stock levels across in-store and online channels. It lives in Supabase (cloud PostgreSQL) so it is always accessible to the desktop app, the GitHub Actions sync script, and future integrations.

---

## Key Concepts

| Concept | Description |
|---------|-------------|
| **On Hand** | Physical units present in the store right now |
| **Allocated** | Units committed to unfulfilled online orders (not yet dispatched) |
| **Available** | `On Hand − Allocated` — what can actually be sold or ordered |
| **Customer Allocation** | Stock reserved for a specific named customer (special order) — tracked separately from online allocation |
| **Web SKU** | The SKU as it appears on Neto/eBay after applying any supplier suffix/prefix |
| **Serial Number** | A unique identifier tied to one specific physical unit of a serialised item |
| **Kit** | A product that is made up of multiple individual inventory items sold together |

## Background Sync Script (GitHub Actions)

> Full detail in [07_online_integration.md](07_online_integration.md). Summary here for inventory context.

- Runs on a cron schedule every 5 minutes
- Fetches all unfulfilled Neto ("Pick" status) and eBay orders
- For each line item:
  - If no matching `online_allocations` record exists → create one and increment `qty_allocated_online` on `items`
  - If an `online_allocations` record exists but the order is now gone → order was cancelled; decrement `qty_allocated_online`
- Script is idempotent — safe to re-run
- Writes a run log to Supabase (`sync_log` table) for debugging

## Dispatch Hook (Existing App Integration)

When an order is marked dispatched in the existing Scarlett AIO:
1. Look up `online_allocations` by order ID
2. For each line: decrement `qty_on_hand` by qty dispatched
3. Delete the `online_allocations` record (this also decrements `qty_allocated_online`)
4. Write a `stock_movements` record of type `dispatch`
5. If the item is serialised: prompt staff to select which serial number was dispatched

## Stock Control

### Manual Stock Adjustment
Any staff member with manager or admin role can adjust `qty_on_hand` for an individual item directly from the Details tab. Every adjustment must include:
- A reason code (`Damaged`, `Lost`, `Found`, `Count Correction`, `Other`)
- Optional free-text notes
- The resulting `stock_movements` record links back to the performing staff member and timestamp

This covers day-to-day discrepancies (damaged goods written off, items found in back-stock, etc.) without requiring a full stocktake.

---

### Invoice Receiving → Stock & Price Update
When a supplier invoice is received and entered via the Purchasing & Receiving module (see [04_purchasing_receiving.md](04_purchasing_receiving.md)), the inventory system is updated as follows:

- `qty_on_hand` incremented by received quantity
- `qty_on_order` decremented accordingly (or zeroed if fully received)
- `last_purchase_cost` updated to the cost on this invoice
- `last_purchase_date` updated
- `average_cost_exc_gst` and `average_cost_inc_gst` recalculated (weighted rolling average)
- A `stock_movements` record of type `receive` is written, referencing the invoice/PO number
- If the item has customer allocations awaiting this stock, a notification is triggered (see [06_customer_special_orders.md](06_customer_special_orders.md))

The invoice entry will also create or update a supplier bill record with payment due date, affecting the accounts payable view in the Purchasing module. The inventory system only holds the stock/price side; financial tracking lives in plan 04.

### Stocktake

#### Initial Stocktake (First-Time Setup)
Before going live with accurate stock counts, all existing `qty_on_hand` values must be zeroed so a clean manual count can be performed. This is a destructive, admin-only operation.

**Zero-out flow:**
1. Admin selects "Prepare for Stocktake" from the inventory menu
2. A clear warning is shown: all On Hand counts will be set to zero; this cannot be undone
3. On confirmation, every item's `qty_on_hand` is set to `0` in a single bulk update
4. A `stock_movements` record of type `stocktake_zero` is written for each affected item (preserving the previous value in `notes`)
5. The inventory screen shows a persistent banner: *"Stocktake in progress — counts may be inaccurate"* until the stocktake is marked complete

**Counting and re-entry:**
- Staff can enter counted quantities item-by-item via the existing inventory UI (using the Adjust Stock button with reason `Count Correction`)
- Alternatively, counts can be imported from a CSV (SKU + counted qty)
- The mobile companion app (see below) is the preferred long-term method

**Completing the stocktake:**
- Admin marks the stocktake complete, which clears the banner
- A `stock_movements` record of type `stocktake_count` is written for each item where qty changed, recording the final counted value

#### Ongoing / Cycle Counts
Periodic partial stocktakes (e.g. count one brand or instrument category at a time) follow the same flow but scoped to a filtered subset of items. The zero-out step applies only to the selected subset.
